你现在要严格按照以下 5 个阶段顺序执行，不能跳跃、不能合并阶段。每个阶段完成后，必须等待用户确认「继续」或提出修改意见后再进入下一阶段。

阶段 1：Bug 分析
─────────────────
→ 调用 agent: bug-analyst
使用用户输入的 Bug 描述 + 报错信息 + 当前代码库上下文，生成完整的 Bug 分析报告（根因定位、影响范围、复现步骤）。
输出格式：保存为 docs/bug-xxx/01-Bug分析报告.md，并展示主要内容。
完成后询问：Bug 分析是否OK？需要修改？输入「继续」进入下一阶段。

阶段 2：修复方案规划
─────────────────
→ 调用 agent: fix-planner
参考 Bug 分析报告 + 知识库中的架构/接口规范，生成详细的修复方案（技术选型、修改文件清单、修复步骤、回滚预案）。
输出：保存为 docs/bug-xxx/02-修复方案规划.md
包含：修改文件清单、核心修复逻辑、潜在风险、回滚方案
询问用户确认。

阶段 3：代码修复
─────────────────
→ 调用 agent: fix-implementer
按照修复方案逐文件/逐模块实现代码修复。
支持增量修复：一次只修改 1-3 个文件，用户确认后继续。
每修复一批文件后，自动 diff 并询问是否应用。

阶段 4：修复验证
─────────────────
→ 调用 agent: fix-verifier
对修复后的代码进行验证（逻辑正确性、是否引入新问题、是否解决根因）。
生成验证报告 → 保存为 docs/bug-xxx/03-修复验证报告.md
如果验证不通过，建议修复 → 返回阶段 3 迭代

阶段 5：回归测试
─────────────────
→ 调用 agent: regression-tester
为修复点编写回归测试用例，确保 Bug 不再复现，且不影响周边功能。
生成测试文件 + 回归测试报告 → 保存为 docs/bug-xxx/04-回归测试报告.md
最后总结整个 Bug 修复的完成度，并建议下一步（git commit / pr 等）

知识库引用规则：
- 每次规划/修复前，必须先 grep / read 知识库中的「架构」「接口」相关 md
- 路径约定：knowledge-base/architecture.md 和 knowledge-base/interfaces.md

开始时先问用户：请描述你要修复的 Bug（现象、报错信息、复现步骤越详细越好），以及 bug 的 slug/name（用于创建文件夹，例如 user-login-null-pointer）。
